Most styling controls in Blicks store a value **per state**, not just one value. Switch the state,
change the control, and you have styled the hover — no custom CSS, no extra block.

## The four states

| State | Fires on | CSS |
|---|---|---|
| **Default** | always | the base rule |
| **Hover** | pointer over the block | `:hover` |
| **Focus** | keyboard focus | `:focus` |
| **Active** | held down / being pressed | `:active` |

The state selector sits at the top of every styling facet, beside the device trio. A dot next to it
tints when you are editing a non-default state, so you cannot forget you left it on hover — a
mistake that otherwise looks like your default styling has broken.

<Note>
Ten of the twelve blocks support all four states. **Divider and Spacer are default-only** — they
have nothing to interact with, so their state selector is not shown at all.
</Note>

## Styling a hover

<Steps>
	<Step title="Select the block and open a styling facet">
		Colors, Effects, Border, Typography — any of them.
	</Step>
	<Step title="Switch the state to Hover">
		Use the selector at the top of the facet.
	</Step>
	<Step title="Change what should differ">
		Only what you change is stored. Everything else keeps falling through to the default value.
	</Step>
	<Step title="Add a transition">
		In **Effects ▸ Transition**, on the *default* state. A transition set on hover only animates the way in, not the way out.
	</Step>
</Steps>

That last step is the one people get wrong. The transition belongs on the default state because it
describes how the block moves between states, not what it looks like in one of them.

## Always pair focus with hover

If a block reacts to the mouse, it should react to the keyboard. Anything you set on hover — a
background shift, a border, a lift — set on focus too, or keyboard users get no feedback that they
have reached it.

<Tip>
Focus is easy to check: click into the page and press <kbd>Tab</kbd> repeatedly. Every interactive
block should visibly change as it takes focus.
</Tip>

## Seeing what a state actually changes

Once a few states carry values, it stops being obvious what is set where — the values are spread
across facets and only visible when that state is selected.

The **States** facet solves this. It lists every override the block stores for the current state,
across all facets and devices, as a plain read of the block's values. Use it to answer "why does
this look different on hover?" without tabbing through every facet with hover switched on.

## States and devices combine

State and device are independent: a value belongs to a state *and* a device. You can style hover
differently on mobile, though you rarely want to — touch devices have no true hover, and a hover
style that only appears after a tap reads as a bug.

Style hover on Desktop and let it inherit. Reach for a per-device hover value only when the desktop
one is actively wrong on a small screen.

## Motion

Two facets handle movement, and they do different jobs:

<CardGroup cols={2}>
	<Card title="Effects" icon="sparkles">
		State-driven change — transition, transform, filter, shadows, opacity, clip path, backdrop filter. This is what makes a hover feel intentional.
	</Card>
	<Card title="Animation" icon="play">
		Keyframe animations from the design system's library: name, duration, easing, iteration, direction, fill mode and delay.
	</Card>
</CardGroup>

Animations run **only when the visitor has not asked for reduced motion**. The whole animation layer
sits behind `prefers-reduced-motion: no-preference`, so a visitor with that system setting on sees
your page without it moving — you do not have to remember to handle it. Scroll-driven timelines are
gated a second time, behind a browser support check, so browsers without them simply show the
un-animated page.

<Warning>
Reduced motion covers keyframe animations. A large transform on hover still runs, because
transitions are not gated the same way — keep hover movement small and quick.
</Warning>
